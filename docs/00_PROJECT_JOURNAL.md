### 설계 결정과 이유

1. Django 서버 렌더링 구조를 확정했다.
   - 공개 사용자의 자체 회원가입이 필수이므로 Sites starter의 인증 모델은 요구사항과 맞지 않았다.
   - Django 내장 인증은 비밀번호 해시, 세션 회전, CSRF와 관리자 권한을 검증된 구현으로 제공한다.
2. 송금은 실제 금융 연동이 아닌 `DEMO POINT` 내부 원장으로 정의했다.
   - 은행계좌·카드·실명 금융정보·PG 비밀키를 수집하지 않으면서 송금 흐름, 잔액, 원자성, 멱등성, 감사 가능성을 구현할 수 있다.
   - 화면과 README에 현금화·충전·출금이 불가능한 과제용 포인트임을 명시한다.
3. 당근·번개장터의 기능을 그대로 복제하지 않고 신뢰 구조만 선별했다.
   - 당근: 쉬운 등록, 개인정보를 노출하지 않는 대화, 차단·신고, 지역 단서.
   - 번개장터: 상세 검색, 거래 상태, 원장성, 관리 처리상태.
   - 제외: 위치 인증을 가장한 표시, 불투명 평판 점수, 실제 결제·택배·검수, 외부 URL 거래 유도.

### 설계에서 구현한 보안 통제

- 공개 저장소에 비밀값이 들어가지 않도록 Django 기본 하드코딩 SECRET_KEY를 제거했다.
- 운영환경은 SECRET_KEY 누락 시 시작을 거부하고, 개발환경은 프로세스마다 임시 키를 생성한다.
- 쿠키·CSRF·CSP·클릭재킹·MIME·캐시 방지 설정을 코드 기본값에 포함했다.
- 사용자 입력을 받는 기능은 모델 필드가 아니라 명시적 Form 허용목록을 사용한다.

## 2026-07-12 - 핵심 기능 구현과 통합

### 수행한 작업

- 공개 회원가입·로그인·POST 로그아웃, 계정·네트워크 단위 로그인 실패 제한, 관리자 계정 정지를 구현했다.
- 상품 등록·검색·상세·수정·soft delete와 이미지 검증·JPEG 재인코딩을 구현했다.
- 상품별 1:1 대화, 개인 차단, 상품·사용자 신고와 관리자 처리 흐름을 구현했다.
- 실제 화폐가 아닌 DEMO POINT를 원자적 이중 원장, 멱등키, 조건부 잔액 차감으로 구현했다.
- Django Admin에서 사용자·상품·대화·신고를 관리하고 송금·원장을 읽기 전용으로 확인하도록 제한했다.

### 이 구조를 선택한 이유

- 인증 주체, 판매자, 메시지 발신자, 신고 대상, 송금 발신자를 요청 필드가 아니라 인증 세션과 URL 문맥에서 결정하면 Mass Assignment와 IDOR 위험을 줄일 수 있다.
- 이미지의 원본 이름·형식·메타데이터를 신뢰하지 않고 디코딩 후 새 JPEG로 저장하면 위장 파일과 개인정보가 포함된 EXIF 노출을 함께 줄일 수 있다.
- 송금 전에 조회한 잔액을 애플리케이션 메모리에서만 믿지 않고 DB 조건부 갱신과 트랜잭션을 사용하면 동시 요청의 이중 사용과 부분 기록을 방지할 수 있다.

## 2026-07-12 - 통합 점검에서 발견한 문제와 변경

### 신고 대상 서버 바인딩

- 발견: `ModelForm.is_valid()`가 모델 `clean()`을 호출하는 시점보다 신고 대상 할당이 늦어 정상 신고가 저장되지 않았다.
- 위험: 대상 필드를 폼에 노출하는 임시 우회는 클라이언트가 신고 대상을 바꾸는 Mass Assignment로 이어질 수 있었다.
- 변경: URL에서 조회한 상품 또는 사용자를 `form.instance`에 먼저 바인딩한 뒤 검증하고, DB의 “대상 정확히 하나” 제약을 함께 유지했다.
- 검증: 신고 대상 변조·중복 제한 테스트를 포함한 Django 테스트가 통과했다.

### 송금 화면 잔액 context

- 발견: 서버 원장의 잔액은 정확했지만 송금 화면에 지갑 context가 전달되지 않아 템플릿 기본값 `0`이 표시됐다.
- 위험: 화면 정보와 서버 판단이 달라 사용자가 잘못된 결정을 할 수 있는 무결성·사용성 문제였다.
- 변경: 인증 사용자의 지갑을 `ensure_wallet()`로 조회해 송금 폼과 함께 전달했다. 송금 승인 자체는 계속 서버 원장 잔액으로 판단한다.
- 검증: `test_transfer_page_uses_authenticated_wallet_balance`에서 소유자와 100,000 포인트 표시용 context를 확인했다.

### 모바일 로그아웃

- 발견: 470px 이하 CSS가 POST 로그아웃 버튼을 숨겨 작은 화면에서 세션 종료 경로가 사라졌다.
- 위험: 공용·분실 기기에서 사용자가 세션을 즉시 종료하지 못할 수 있었다.
- 변경: 해당 숨김 규칙을 제거하면서 POST와 CSRF 보호는 그대로 유지했다.
- 검증: 반응형 CSS 규칙과 로그아웃 폼을 재검토하고, GET 로그아웃 405·POST 로그아웃 성공 테스트를 확인했다.

### 폼 ARIA 연결

- 발견: Django 5.2 위젯은 `_helptext`, `_error` ID를 `aria-describedby`로 참조하지만 템플릿이 다른 ID를 사용하거나 오류 ID를 만들지 않았다.
- 위험: 스크린리더 사용자가 입력 도움말과 검증 오류의 관계를 정확히 알기 어려웠다.
- 변경: 도움말 ID를 Django 규약과 일치시키고 여러 오류를 하나의 `_error` 컨테이너로 묶었다.
- 검증: 전체 템플릿 파싱과 렌더링된 위젯의 ARIA 참조를 대조했다.

### 운영 HSTS

- 발견: 1년 HSTS는 있었지만 하위 도메인과 preload 적용이 고정 비활성화되어 운영 배포 검사 기준이 완전하지 않았다.
- 변경: 운영환경 기본값을 1년 HSTS, `includeSubDomains`, `preload`로 설정하고 환경변수로 단계적 운영 전환이 가능하게 했다.
- 이유: HTTPS 강제 정책을 코드 기본값으로 보장하되, 모든 하위 도메인의 HTTPS 준비 여부를 운영자가 통제할 수 있어야 하기 때문이다.
- 검증: 비밀이 아닌 검증용 환경값으로 `manage.py check --deploy`를 실행해 문제 0건을 확인했다.

## 2026-07-12 - 2차 위협 모델 점검과 방어 심화

### 관리자 권한과 계정 불변식

- 이유: Django Admin에 로그인했다는 사실만으로 신고 모델을 통해 다른 모델의 상품 차단·사용자 정지를 수행하게 해서는 안 된다. 또한 일괄 작업이 현재 관리자·staff·superuser를 정지시키면 관리 권한 복구가 어려워진다.
- 변경: 신고 변경 권한과 함께 전용 `market.block_listing` 또는 `accounts.suspend_user` 권한을 작업 내부에서 다시 검사하고, UI에서 숨긴 작업도 위조 POST로 호출하지 못하게 했다. 현재 사용자·staff·superuser는 일괄 정지 대상에서 제외했다.
- 추가 변경: 관리자 로그인도 일반 로그인과 같은 계정 5회/15분·네트워크 원시도 30회/15분 HMAC 제한을 사용한다. 성공은 해당 계정 상태만 지우고 네트워크 누적은 유지한다. `is_suspended=True`이면 `is_active=False`여야 한다는 DB CHECK 제약과 데이터 마이그레이션을 추가했다.
- 검증: 교차 모델 권한 없음·위조 POST·두 권한 보유·보호 계정·관리자 로그인 제한·DB bulk update 거부 테스트가 통과했다.
- 잔여 위험: 운영에서는 최소 권한 그룹을 별도로 만들고 superuser 사용을 긴급 작업으로 제한해야 한다.

### 자원 고갈과 공개 범위

- 이유: 회원가입·상품 등록·메시지·신고가 무제한이면 저장소와 DB를 소진할 수 있고, 단순 `is_staff`만으로 비공개 상품을 조회시키면 staff 역할이 과도한 권한을 얻는다.
- 변경: 가입은 네트워크당 시간당 5회, 상품 등록은 사용자당 시간당 10회로 제한했다. 계정별 공개·보관 상품은 각각 50·500개로 제한하고 계정 행 잠금 안에서 수량을 다시 계산한다. 메시지는 분당 20·일 500, 신고는 일 10으로 제한한다.
- 추가 변경: 비공개 상품 조회는 `market.view_listing` 권한이 있는 사용자만 허용하고, 정지·비활성 판매자의 상품은 목록·상세·이미지·찜·새 대화에서 숨긴다.
- 검증: 가입·상품 rate/quota, 권한 없는 staff의 차단 상품 조회 거부, 정지 판매자 상품 비공개 테스트가 통과했다.
- 잔여 위험: 개발의 LocMem cache는 다중 프로세스에 공유되지 않으므로 운영에서는 Redis 등 원자적 공유 cache와 PostgreSQL을 사용해야 한다.

### 상품 상태·TOCTOU·이미지 생명주기

- 이유: 편집 화면을 연 뒤 관리자가 상품을 차단해도 오래된 POST가 차단 상태를 되돌리거나 내용을 덮어쓰는 TOCTOU 위험이 있었다. 판매자는 거래 상태를 명시적으로 바꿀 기능도 필요했다.
- 변경: 수정·삭제 시 트랜잭션 안에서 상품을 다시 잠그고 현재 소유자·상태를 재검증한다. 판매 상태는 POST 전용 허용 전이 `판매중↔예약중`, `판매중/예약중→판매완료`, `판매완료→판매중`만 허용한다.

## 2026-07-12 - 3차 적대적 보안 감사와 증거 보존

### 인증 제한과 관리자 최소권한

- 이유: 단순히 “5회 잠금”을 구현해도 비밀번호 hash 중 DB transaction을 유지하거나 성공 시 네트워크 counter를 지우면 SQLite 가용성 저하와 유효 계정을 이용한 제한 우회가 생긴다. 실제/미존재 계정의 DB 경로가 다르면 계정 열거도 가능하다.

### 신고 시점 상품 증거

- 이유: 판매자가 신고 직후 제목·설명·이미지를 바꾸거나 지우면 관리자가 원 신고 대상을 검증할 수 없다. 반대로 OPEN 신고 동안 상품 전체를 동결하면 아무 사용자나 신고로 판매자를 방해할 수 있다.
